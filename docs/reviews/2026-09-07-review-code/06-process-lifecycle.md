## Critical (1)
- [dim 2] launcher.py:103 — os.environ.setdefault('PYSTRAY_BACKEND','appindicator') under a comment saying "On Linux", but THERE IS NO PLATFORM GUARD. pystray honours the variable by importing pystray._<name> unconditionally and does NOT fall back when a named backend fails; _appindicator begins with `import gi`, absent on Windows and macOS. So on both, run_tray raises ImportError, launcher.py:140's except Exception swallows it to INFO, the app runs headless — and launcher.py:153 then opens a browser tab on EVERY launch. Breaks CHANGELOG v1.1.0's tray-on-three-platforms promise, DESIGN 3's per-OS backend table, spec 9, and CHANGELOG [Unreleased]'s "no longer opens a browser tab". The spec is complicit (2.1 quotes the unguarded setdefault) but the CODE is the wrong side — spec 9 and DESIGN 3 say what the behaviour must be.

## High (2)
- [dim 16] server_control.py:64 — restart is broken on the AppImage, the primary Linux release format. build-linux.sh:88 generates exec "$HERE/usr/bin/Contact-List", where $HERE is the type-2 runtime's ephemeral mount. Frozen, both sys.executable and sys.argv[0] are that mount path. The child is spawned, then os._exit(0) ends the payload, the runtime unmounts, and the child — a onedir bundle paging in stdlib and .so files from that vanishing directory — dies part-started. Secondary: sys.executable == sys.argv[0] when frozen, so the command is [binary, binary]. Third: re-exec'ing the old mount reloads the OLD code even when an update succeeded.
- [dim 8] launcher.py:123 — server_thread is non-daemon and NO exit path other than tray-Quit calls server.shutdown(). run.sh execs launcher.py in the foreground. Ctrl-C raises KeyboardInterrupt in the main thread, which is blocked in join() at :134 or :155; the exception unwinds out of main(), and interpreter shutdown then joins the same non-daemon thread still inside serve_forever(). The process HANGS, still serving, after printing a traceback. Only exit is kill.
## Medium (3)
- [dim 16] server_control.py:63-73 — a successful Popen is treated as a successful restart, then os._exit(0). Popen returning only proves execve succeeded; a child that then fails leaves NO server, and frozen builds have no console. The except OSError covers one failure mode of three. On the CL-0054 race specifically: neither hardening the roadmap names has landed.
- [dim 7] browser.py:37-44 — neither route is checked and neither failure recorded. xdg-open exiting non-zero is indistinguishable from success, so the webbrowser fallback never runs; webbrowser.open's False return is discarded. - [dim 16] launcher.py:123 — nothing observes the server thread's death. If serve_forever raises, threading.excepthook writes to a sys.stderr that is None on a frozen windowed build, and the main thread carries on running the tray: a live icon in front of a dead server.
